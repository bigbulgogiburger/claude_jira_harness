# Jira 이슈 작성 베스트 프랙티스

라벨 / 날짜 / 설명 포맷 / 우선순위 등 부가 필드의 컨벤션을 정리한다.

## 라벨 (Labels)

### 기본 원칙

1. **소문자 + kebab-case 통일** — 라벨은 case-sensitive 다. `Spring-Boot`, `Spring_Boot`, `springBoot`, `spring-boot` 가 전부 다른 라벨로 잡힌다. 한 번 결정한 표기를 유지한다.
2. **공백 사용 금지** — Jira 라벨에는 공백을 넣을 수 없다. `tech debt` 가 아니라 `tech-debt`.
3. **짧고 의미 있게** — 1-3 단어. 길어지면 컴포넌트 필드를 쓰는 게 낫다.
4. **prefix 패턴 권장** — 큰 카테고리는 prefix 로 묶으면 검색이 쉬워진다 (예: `area-backend`, `area-frontend`).

### 권장 라벨 카테고리

| 카테고리 | 예시 | 용도 |
|---------|------|------|
| **stack** | `spring-boot`, `vue`, `react`, `flutter`, `python`, `go`, `rust` | 언어/프레임워크 |
| **area** | `backend`, `frontend`, `mobile`, `infra`, `docs`, `db` | 작업 영역 |
| **kind** | `feature`, `bug`, `tech-debt`, `refactor`, `chore`, `docs`, `perf`, `security` | 작업 종류 |
| **scope** | `quick-win`, `breaking`, `experimental` | 영향 / 위험 |
| **source** | `from-doc-<basename>`, `from-incident`, `from-customer` | 출처 (콜론 사용 금지 — 라벨 안전 문자만) |
| **사용자 정의 prefix** | `team-cs-`, `app-mobile-`, `q1-2026-` | 팀/스프린트별 분류 |

### 피해야 할 라벨

- 이슈 타입과 중복: `bug` 라벨은 issueType `Bug` 와 중복. 단, 영역 표시(`bug-frontend`)는 OK.
- 우선순위와 중복: `urgent` 같은 라벨 대신 `priority` 필드 사용.
- 너무 일반적: `important`, `todo`, `wip` — 의미가 없다.
- 임시 코드네임: 시간 지나면 의미 잃는다.

### 6개월마다 정리 (감사)

라벨은 누구나 만들 수 있어 시간이 지나면 chaos 가 된다. 6개월에 한 번 라벨 목록을 검토해 중복/오타/사장된 라벨을 정리한다.

## 우선순위 (Priority)

표준 5단계: `Highest`, `High`, `Medium`, `Low`, `Lowest`. 프로젝트마다 다를 수 있으니 메타 확인.

### 매핑 가이드

| 사용자 표현 | 우선순위 |
|-----------|---------|
| "긴급", "ASAP", "블로커", "지금 바로" | `Highest` |
| "급함", "빨리", "중요" | `High` |
| (명시 없음) | (설정 안 함, 기본값) |
| "여유 있어", "나중에", "사소" | `Low` |
| "언젠가", "Nice to have" | `Lowest` |

> 명시되지 않은 경우 우선순위를 임의로 설정하지 않는다. 프로젝트 기본값(보통 `Medium`)을 사용하게 둔다.

## 날짜 (Start date / Due date)

### 핵심 결론

**기본적으로 설정하지 않는다.** 사용자가 일정을 명시한 경우에만 설정한다.

### 시스템 필드 vs 커스텀 필드

| 필드 | 키 | 비고 |
|-----|------|------|
| **Due date** | `duedate` | 시스템 기본 필드. 백로그/보드/JQL에서 동작. **이걸 써야 한다.** |
| **Start date** | 보통 `customfield_10015` | 커스텀 필드. 키가 프로젝트마다 다를 수 있다. |
| Target start / Target end | 다양함 | Advanced Roadmaps용. 일반 작업에선 굳이 안 씀. |

### 권장 사항

- **Due date 만 사용**: 시스템 필드라 안전하고 백로그/보드에서 잘 보인다.
- **Start date 는 손대지 않는다**: 키가 프로젝트마다 달라 충돌 위험. 정말 필요하면 사용자에게 키를 직접 받는다.
- **포맷**: `YYYY-MM-DD`. Atlassian REST API 표준 ISO 형식.
- **상대 날짜는 절대화**: 사용자가 "다음주 금요일까지" 라고 하면 오늘 날짜 기준으로 절대 날짜로 변환해서 입력. (오늘 날짜는 시스템 컨텍스트에서 확인.)

### 등록 예시

```json
{
  "additional_fields": {
    "duedate": "2026-05-22"
  }
}
```

## 컴포넌트 (Components)

라벨보다 더 구조화된 분류. 프로젝트 관리자가 정의한 목록에서 골라야 한다.

- 라벨이 자유 입력 / 컴포넌트는 통제된 어휘.
- 컴포넌트는 자동 담당자 매핑(component lead)도 가능.
- 사용자가 명시하지 않으면 굳이 자동 부여하지 않는다 — 프로젝트마다 정의가 달라 잘못 매기면 라벨보다 더 정리하기 귀찮다.

## 설명 (Description) 포맷

### 마크다운 vs ADF

`mcp__atlassian__createJiraIssue` 의 `contentFormat` 파라미터:

- **`"markdown"`** ← 권장. 가독성 좋고, 줄바꿈/목록/체크박스/링크/코드블록 모두 지원.
- `"adf"` (기본값): JSON. 프로그래매틱 처리에는 좋지만 사람이 읽고 쓰기 어렵다.

**항상 `"markdown"` 으로 보낸다.** ADF JSON 을 직접 만들지 않는다.

### 마크다운 작성 시 주의

1. **리터럴 `\n` 금지**: 문자 그대로의 `\n` 을 description 안에 넣으면 줄바꿈이 아니라 그 텍스트 그대로 보인다. **실제 개행문자**를 사용한다.
2. **체크박스**: `- [ ]` 와 `- [x]`. Jira 에디터에서 인터랙티브 체크박스로 렌더링.
3. **헤딩**: H1(`#`)은 제목과 중복되니 H2(`##`)부터.
4. **링크**: `[텍스트](URL)` 표준 마크다운. 이슈 키(`PROJ-247`)는 그냥 적어도 자동 링크.
5. **코드**: 인라인 백틱 `` `code` `` 또는 펜스 ``` ``` ```python ... ``` ``` ```.

### 권장 섹션 (이슈 타입별)

| 이슈 타입 | 권장 섹션 |
|---------|----------|
| **Epic** | 목표, 성공 지표, 범위, 범위 외, 관련 |
| **Story** | 사용자 가치, 작업 범위, 인수조건, 참고 |
| **Task** | 배경, 작업 범위, 인수조건, 참고 |
| **Bug** | 재현 절차, 기대 동작, 실제 동작, 환경, 영향 |
| **Sub-task** | (짧게) 작업 내용, 인수조건 |

자세한 템플릿은 `description-templates.md`.

## 인수조건 (Acceptance Criteria)

### 두 가지 표준 포맷

#### 1. 체크리스트 (가장 보편적)

```markdown
## 인수조건
- [ ] 사용자가 이메일과 비밀번호로 로그인할 수 있다
- [ ] 잘못된 자격증명 입력 시 명확한 에러 메시지가 표시된다
- [ ] 로그인 성공 시 대시보드로 리다이렉트된다
```

언제 쓰나: 대부분의 경우. 진행 상황을 시각적으로 추적할 수 있다.

#### 2. Given-When-Then (BDD 스타일)

```markdown
## 인수조건

**시나리오 1: 정상 로그인**
- **Given** 등록된 사용자가 로그인 페이지에 있을 때
- **When** 올바른 이메일과 비밀번호를 입력하고 로그인 버튼을 누르면
- **Then** 대시보드 페이지로 리다이렉트된다

**시나리오 2: 잘못된 비밀번호**
- **Given** 등록된 사용자가 로그인 페이지에 있을 때
- **When** 올바른 이메일과 잘못된 비밀번호로 로그인을 시도하면
- **Then** "이메일 또는 비밀번호가 올바르지 않습니다" 메시지가 표시된다
```

언제 쓰나: 사용자 행동 흐름이 중요한 기능. QA 팀이 이 형식을 선호하면 쓴다.

### 좋은 인수조건의 조건

- **검증 가능 (Verifiable)**: 패스/페일을 확정할 수 있다.
- **단일 (Single)**: 하나의 항목 = 하나의 검증 포인트. "X 가 되고 Y 가 된다" 처럼 묶지 말고 분리.
- **관찰 가능 (Observable)**: 내부 구현이 아니라 외부에서 보이는 행동.
- **모호하지 않음**: "잘 동작한다" / "빠르다" / "사용자 친화적" 같은 표현 금지.

## 제목 (Summary) 작성

### 길이 / 형식

- **70자 이내** (외부 도구/이메일에서 잘리지 않는 길이)
- **컴포넌트 prefix**: `[Dashboard]`, `[Settlement]`, `[API]` — 빠른 스캔 + 그룹핑
- **버그는 "X 가 Y 됨" 형태**: 증상이 명확하게
- **기능은 "X 추가" / "X 개편" / "X 분리"**: 행동이 명확하게

### 좋은 예 / 나쁜 예

| 나쁜 예 | 좋은 예 |
|---------|---------|
| "대시보드 수정" | "[Dashboard] KPI 위젯 추가" |
| "버그" | "[정산] 엑셀 다운로드 시 한글 파일명 깨짐 (Safari 16+)" |
| "API 작업" | "[API] KPI 집계 엔드포인트 추가" |
| "리팩터링" | "[Settlement] SettlementService Read/Write 분리" |

## Issue Type 선택

표준 타입과 사용 기준:

| 타입 | 사용 기준 |
|-----|---------|
| **Epic** | 여러 스토리/태스크를 묶는 큰 이니셔티브. 보통 1-3 스프린트 분량. |
| **Story** | 사용자에게 가치를 주는 기능 단위. "유저로서 X 를 할 수 있다." |
| **Task** | 사용자에게 직접 보이지 않는 기술 작업. 인프라 / 리팩터링 / 마이그레이션. |
| **Bug** | 기대와 다른 동작. 재현 절차 필수. |
| **Sub-task** | 한 Story/Task 내부의 세부 작업. 다른 사람이 분담 가능할 정도일 때만 만든다. |

> Story 와 Task 는 형제다. 둘이 헷갈릴 땐 "외부 가치인가 (Story) / 내부 작업인가 (Task)" 로 결정.

## 담당자 (Assignee)

- 사용자가 명시하지 않으면 비워둔다 (또는 자동 매핑되게 둔다).
- 담당자 ID 는 `getJiraIssue` 의 `fields.assignee.accountId` 또는 `lookupJiraAccountId` 로 확인.

## 한국어 작성 톤

- **요구사항/설명은 한국어**, 단 코드/디렉토리/패키지/엔드포인트 이름은 영문 그대로.
- 명령조 또는 평서문 — 결정은 일관되게.
- 외래어는 한국 IT 업계 관용 표기 (예: "리팩터링", "디버깅", "리뷰", "머지").
- 줄임말 남발 금지 — Jira 검색 정확도 떨어진다.

## 흔한 실수 모음

1. ❌ description 에 리터럴 `\n` 박힘 → ✅ 실제 개행 사용
2. ❌ 라벨에 공백 (`tech debt`) → ✅ kebab-case (`tech-debt`)
3. ❌ Story 아래에 Task → ✅ 둘 다 Epic의 자식이고 형제다
4. ❌ Sub-task가 1개뿐 → ✅ 부모 본문 체크리스트로
5. ❌ description 에 5페이지짜리 설계 문서 → ✅ 라이트하게 (jira-clarify, jira-plan 이 채울 것)
6. ❌ 사용자 확인 없이 등록 → ✅ 항상 드래프트 보여주고 승인
7. ❌ 시스템 `duedate` 대신 커스텀 필드 → ✅ `duedate` 사용
